# P4-6a QQ 入口对齐主线

QQ 入口已对齐微信主线：真实文本 provider 可装配、进程始终以暂停态启动并由只读探针看守、`/healthz` 如实报告模式与 worker、本机常驻栈可按平台切换。**没有连接真实 NapCat、没有登录、没有真实发送、没有调用付费模型**：所有平台交互都在测试里用假 OneBot HTTP 服务完成。范围见 [开发计划 §4.2](../development-plan.md#42-p4-6-qq-系列当前优先)。

## 交付

### 01：只读 OneBot 探针（新增 `packages/platform/qq/onebot-probe.mts`）

看门狗只问一个问题：**这个 OneBot 端点是否仍以本桥接代表的账号登录？** 为此该模块**只允许一个动作** `get_login_info`，不提供通用 action 调用器。

- 端点边界与传输一致：http/https、无凭据/查询/片段、路径必须是 `/`；token 非空且不含换行；`selfId` 必须是十进制数字串；回包上限默认 64 KiB、有超时、`redirect: 'manual'`。
- 判定只看 ID 关系：`status==='ok' && retcode===0` 且 `data.user_id`（字符串或数字）等于 `QQ_SELF_ID` 才算登录正常。**回包正常但账号不符返回 `false`**（这是明确答案，交给看门狗记 `HOOK_LOGIN_ABNORMAL`）；非 200、非 JSON、超大、空回包、空 `user_id`、`retcode!==0` 一律抛错（记 `HELPER_UNRESPONSIVE`）。
- 进程检查：给了 `pid` 才检查（默认 `process.kill(pid,0)`），**不给就视为存活**——NapCat 可能不由本栈托管，猜一个 pid 只会把健康账号误判为 `PROCESS_EXITED`。
- 类型上不反向依赖 apps：模块内声明与看门狗 `HealthProbe` 结构相同的 `OneBotHealthProbe`。

11 项单测覆盖固定动作、不跟随重定向、账号不符、字符串/数字 ID、四种畸形回包、非 200/非 JSON/空回包、超大回包、取消传播、pid 开关，以及端点/token/selfId/pid/上限的构造期拒绝。

### 07：桥接装配（`apps/bridge/bridge.mts`）

- `intelligence?: PersistentIntelligence` 可选；**默认仍是持久假模型**，已有调用方不受影响。
- `startPaused`、`watchdog`、`onWatchdogFatal` 与微信侧同形；`start()` 顺序照搬：写 `BRIDGE_RESTARTED` → `recover` → `watchdog.tick`（致命即抛）→ `watchdog.start` → outbox → worker。
- worker 只在出站装配时创建：`dispatch` 是显式形式，**只传 `workerIntervalMs` 视为要求 worker**（保持既有调用方与用例不变）；没给出站时不再创建"一定会拒绝发送"的 worker。
- `/healthz` 返回 `{status, adapter, mode, worker, watchdog?}`，致命时 503，且**不含 QQ 号、token 或 URL**；`POST /onebot/event` 在看门狗致命时同样 503。

### 07：入口（`apps/bridge/main.mts`）

- `QQ_INTELLIGENCE`（`persistent-fake` | `deepseek`，默认 fake，其他值 `UNSUPPORTED_INTELLIGENCE_PROVIDER` 启动失败）。`deepseek` 时复用微信侧同一套 `readDeepSeekEnv`/`describeDeepSeekEnv`/`createDeepSeekFromEnv`/`createTextModelIntelligence`，日限额自动生效；只打印一行脱敏 provider 描述，每次调用只输出 `model_call` 度量。
- 探针在配置了 `QQ_ONEBOT_HEALTH_URL`（默认取 `QQ_ONEBOT_BASE_URL`）时启用；只接收模式没有地址就不启用。`QQ_PROCESS_ID` 可选且必须为正整数。
- 默认 `startPaused: true`；看门狗致命时退出码 1。`QQ_QUIET_MS`、`QQ_WATCHDOG_INTERVAL_MS` 默认与微信一致。启动行追加 `watchdog enabled|disabled`。

### 07：本机常驻栈（`scripts/local-stack-driver.mts`、`local-stack.mts`）

- `LOCAL_BRIDGE_PLATFORM`（默认 `wechat`，只接受 `wechat`/`qq`）；`config.platform`、`config.bridgeEntry` 随之切换，`CORE_PLATFORM` 跟随。
- 必填变量按平台切换：QQ 要 `QQ_ACCOUNT_ID`/`QQ_SELF_ID`/`QQ_BRIDGE_TOKEN`；开启 `QQ_ENABLE_OUTBOUND=1` 时另要 `QQ_ONEBOT_BASE_URL`（微信侧对应 `WECHAT_*` 与 `WECHAT_WXHELPER_BASE_URL`）。
- 入口选择不再写死 `wechat-main.mts`；`local-stack.mts` 头注释说明平台切换与"两个平台不同时跑"。

关键覆盖点：

- **真实 provider 路径**：注入 `createTextModelIntelligence(createDeepSeekTextProvider({ fetchImpl }))`，一条来信产生 1 个待确认任务、1 次模型请求、1 条度量；并断言**正文与生成内容都不出现在度量里**。无计费调用。
- **三类故障码**：假 OneBot 分别以进程不在、答复晚于探针超时、`user_id` 不符触发 `PROCESS_EXITED`、`HELPER_UNRESPONSIVE`、`HOOK_LOGIN_ABNORMAL`，逐个断言写入 `orch_account_health` 且会话保持 `ACCOUNT_FAULT` 暂停；恢复探测后账号仍需本人恢复。
- **致命收敛**：持久化失败后 `/healthz` 与 `/onebot/event` 都是 503。
- **重启不会自己恢复**：先健康登记会话，再用第二个 bridge 实例重跑 `start()`，断言账号仍处暂停（只有本人能恢复）。
- **栈配置两分支**：默认仍是微信入口与 `CORE_PLATFORM=wechat`；`qq` 切到 `apps/bridge/main.mts` 与 `CORE_PLATFORM=qq`；缺 QQ 变量、平台值非法、开启出站但没有 OneBot 地址、以及微信侧缺变量各自报固定错误码。

## 过程中修正的两处（都不是产品缺陷）

1. **看门狗的 `HOOK_LOGIN_ABNORMAL` 需要时钟推进**：该校验前提是"端点已安静 `quietMs`"，最初把 `now` 固定成常量，差值恒为 0，看门狗按设计提前返回、不写记录，于是断言读到上一轮的残留故障码。测试改用推进的时钟。
2. **假 OneBot 的"无响应"不能靠挂住 socket**：悬挂请求会占住连接池，把下一例的探测拖成超时，导致 `HOOK_LOGIN_ABNORMAL` 被误记成 `HELPER_UNRESPONSIVE`。改为"答复晚于超时"——socket 最终正常关闭。

## 边界与未做

- 探针**只**支持 `get_login_info`；不做发送/取媒体等任何通用调用。
- `owner_message_signal` 能力仍为 unknown，**AC16 不因本卡通过**。
- 不新增迁移、依赖、公共事件或构建产物；未改任何微信文件（`wechat-bridge.mts`/`wechat-main.mts`/`packages/platform/wechat/*` 全程只读参照）。
- QQ 系统回显（P4-6b）、QQ 图片原件获取（P4-6c）、表情发送（P4-6d）不在本卡。
- 真实 NapCat 登录、注入、真实发送与真机原图核对**均由本人执行**，本卡不触碰。真机复测时需观察"回显比 HTTP 回包先到"的先后顺序（P4-6b 的竞态）。
