## 1. 总体路线

核心判断：发送安全（租约、账本、未知结果暂停、隔离）已经做得很扎实，但**回复好不好用从未验证**。所以先让它成为本人每天真在用的确认模式工具，用试用数据决定后面投入哪里；功能开发全部在本人电脑上完成，最后再决定部署到哪里。

```text
P0 工程底座 ──┐
              ├─> P1 真实闭环验收 ─> P2 本机试用期（1–2 周）─> P3 小范围自动模式 ─> P4 扩展功能 ─> P5 常在线部署 ─> P6 收尾
P2 开发任务 ──┘   （P2 的开发任务可与 P0/P1 并行，试用本身要等 P1 通过）
```

P0–P4 全部在本人电脑上运行：电脑开着才收信、出候选和发送；关机或休眠时什么都不做，重启后按现有机制「启动即暂停」，不会补发。

| 阶段 | 目标 | 退出门槛（本人判定） |
| --- | --- | --- |
| P0 工程底座 | 文档只有一个状态入口；决策记录与事实一致；基线确认是绿的 | README 和本计划没有互相矛盾的数字；本机完整门禁 0 fail、0 skip |
| P1 真实闭环验收 | 真实来信 → 真实 DeepSeek 候选 → 本人确认 → 真实微信发送 → 核对 → 恢复，在同一次流程内完成 | 一次走通，账本、`model_call`、待办、核对记录相互对得上，有报告 |
| P2 本机试用期 | 1–3 个真实联系人只开确认模式，电脑开机时日常使用，积累质量数据 | 有质量基线报告（采用率、修改幅度、弃用原因、单条成本和时延）；本人据此定 D08 门槛，并决定 P4 的优先顺序 |

## 附录 B：验收记录规则

每条 AC 记录 `not-run/pass/fail/blocked`，环境 `unit/integration/mock-e2e/wechat-real/qq-real`，以及代码 commit、契约版本、数据夹具、步骤、期望与实际、日志 correlationId、截图或回执、已知限制。`pass(mock-e2e)` 不能汇总为平台通过；平台能力不足时记为 blocked 或 fail，不能改期望来通过。证据矩阵见 [acceptance-matrix.csv](reports/acceptance-matrix.csv)。

权限、隔离、重复、旧方案、接管、暂停、未知发送类用例必须全部通过，才可对任何联系人开启自动模式。初次真实运行只选少量联系人、只开确认模式；本人逐个评审后才启用自动。回滚方式：全局暂停 → 停止桥接派发 → 保留入站和审计 → 恢复上一可用版本；数据库回滚不能丢失已提交的发送事实。
