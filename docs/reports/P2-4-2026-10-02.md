# P2-4 本机常驻与看门狗交付

本卡完成本机开发入口与便携 watchdog，未执行真实微信操作或付费模型调用。范围扩展及迁移编号由总控审定，见 [提案](P2-4-proposal-2026-10-02.md)。

## 行为与用法

`npm run serve:local` 按既有 PostgreSQL → 迁移 → 核心 readyz → 微信桥接 healthz 启动；任一受管子进程退出后逆序停整组，再以最大 30 秒的指数退避重启。只停止自己创建的子进程，不接管占用端口的外部服务，不创建集群、不启动/登录微信或注入 helper。每轮核心强制全局暂停，桥接强制账号暂停；终止守护自身后不会自动复活。

新增环境配置及人工演练步骤见 [运行手册](../../deploy/runbook.md#本机常驻与故障演练p2-4)。脚本专用于当前 Windows 开发机，检测逻辑本身不绑定宿主。默认只接收，未把出站开启写进任何默认项。

watchdog 每 10 秒检查本人指定微信 PID 及回环 `api/checkLogin`，超时 3 秒；固定故障为进程退出、helper 不响应/响应异常、无有效回调达 5 分钟且登录探测非 1。只有安静而登录正常不会判故障。探测没有 hook、登录、注入或发送能力。持久化故障失败时进入永久 fatal，停止派发 worker，健康入口/入站返回 503；生产进程退出，交给守护重新以暂停状态启动。

02 在派发一致性锁内记录账号状态，暂停同账号所有联系人、抬高 epoch/代次、使旧方案失效、取消未提交部分，保留未知发送；重复故障不重复抬高代次。后来登记的联系人也继承账号暂停。探测恢复只改健康记录，故障总览继续显示等待本人恢复。未健康时禁止清除 ACCOUNT_FAULT，未知发送仍禁止恢复；其他暂停原因不被顺带清除。

总览只展示固定故障摘要，不泄漏账号/联系人标识。所有已登记账号都有健康记录时 faultQueryStatus 才为 ready；未覆盖时仍 unavailable，不能把空列表当健康证明。连接投影仍未提供。

日志白名单投影后按 1 MiB/5 个副本轮转；保留固定进程事件及安全模型成本/关联指标，丢弃未知 stdout/stderr 原文。日志写入失败停止整组；Windows ACL 仍需本人配置。试用报告可以读取这些轮转日志，指标缺失仍保持未知。数据库中的发送账本与审计不受日志轮转影响。

## 改动与验收

- bridge 新增 watchdog 与 3 项测试；生产入口要求 WECHAT_PROCESS_ID，在 DLL 指纹守护通过后才创建探测器；既有二进制拒绝测试保持通过。
- scripts 新增本机启动器、监督循环/轮转日志及 3 项测试，覆盖启动/停止顺序、失败不启动依赖、退避封顶、停止失败不重叠启动、日志界限与隐私投影。
- 02 增加账号健康命令与故障总览；新增迁移 `0012_account_health.sql`，0013 未分配；无新增依赖或公共契约变更。
- 新增 1 项隔离真实 PostgreSQL 集成用例，覆盖待确认/已确认任务失效、未知任务保留、账号隔离、重复故障幂等、后来登记联系人、健康恢复不自动解除、人工恢复闸、桥接重启即暂停、持久化失败后 503。发送次数为零。
- fixture HTTP 模拟三类故障与恢复，仅调用 checkLogin；真实 PG 集成通过同一 fixture 探测器验证三类错误码落库与暂停。测试的进程存活状态为模拟值，不使用微信进程。
