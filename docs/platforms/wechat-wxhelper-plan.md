# 微信 wxhelper 路线计划

日期：2026-09-24。状态：**路线已由本人选定，但尚未通过第 0 步**。在此之前不下载、不安装、不注入、不登录、不发送。本文件是计划与中止条件，不是能力结论；微信能力仍以 [platform-wechat-capability-snapshot-2026-09-24.json](../reports/platform-wechat-capability-snapshot-2026-09-24.json) 的六族 `unknown` 为准。

## 0. 第一道门禁：先过登录，再过版本（登录已由本机实测解除）

只读核查（2026-09-24，GitHub 仓库与 issue，未安装未运行）得到的门禁事实：

> 2026-09-24 本人确认：主力机上安装的就是 3.9 客户端且能正常登录 → **"新环境新账号登不上旧版"这条门禁在本人机器上不成立**。于是在本机这条路线剩下的门禁变成"客户端版本是否有匹配的偏移"与"能不能自己编译"，见下面的第 0.5 步。

| 事实 | 证据 |
| --- | --- |
| 上游只支持微信 3.9.x | 分支列表最新为 `dev-3.9.11.25`（最后提交 2024-09-12）；带预编译 DLL 的 release 最新为 `3.9.10.19-v1`（2024-05-22）；README 功能表列的是 3.8.0.41–3.9.5.81 |
| **新环境的新账号很可能直接登不上旧版** | 打开状态的 issue：2025-12-26「3.9.5.81微信 新环境 新账号 无法过绕低版本」、2025-12-04「微信版本过低如何解决」 |
| 上游没有 4.x 计划 | 2026-07-28「新版本4.1.11.55支持吗？」与 2026-07-27「支持4.0吗」均无实现；`main` 最后一次实质提交在 2025-04（一个 CVE 修复） |
| 4.x 备选都不成立 | `aixed/WeChat-Hook` 声称支持 4.1.10.27 但**无许可文件**；`likohank/wxhelper_modular_new`（MIT，2★）只是 4.1 的**骨架框架**，内置 API 仅 contacts / profile / status，没有收发模块 |

结论：**登录门禁先于任何 hook 能力**。在独立环境用测试小号做一次登录实测之前，不能假定这条路线可用，也不应该投入适配器开发。

### 第 0.5 步：本机版本与工具链核查（2026-09-24，只读完成）

本人改用主力机直测后，只读核查本机与上游的实际匹配度，结果：

| 项 | 事实 |
| --- | --- |
| 本机微信 | `C:\Program Files (x86)\Tencent\WeChat\WeChat.exe`，**FileVersion 3.9.11.17**（ProductVersion 3.9.11.1000），**x86 客户端**，可登录（进程在运行） |
| 上游版本覆盖 | 最新分支 `dev-3.9.11.25` 的 `offset.h` 只支持 `V_3_9_8_25 / V_3_9_9_43 / V_3_9_10_19 / V_3_9_11_19 / V_3_9_11_25` → **3.9.11.17 不在其中**（差两个补丁号） |
| 预编译产物 | release/tag 最新只到 `3.9.10.19-v1`（2024-05-22），**3.9.11.x 线没有任何预编译 DLL** → 必须自己编译 |
| 本机工具链 | 装有 VS2022，但 `vswhere -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64` 无结果（**缺 C++ 生成工具工作负载**）；`cmake`、`vcpkg` 均未安装 |

推论：wxhelper 在本机**走得通但要先补两件事**——补 C++ 工具链，以及处理"客户端版本 17 / 代码版本 19"的偏移差异。偏移不匹配的失败表现通常是**微信进程崩溃或接口全 404**，不是安静地降级。

**警告**：不要点微信的"检查更新"／"升级"——腾讯当前只会把 3.9 线推到 4.x，一旦升上去这条路线立刻失效，且没有可信渠道拿回 3.9 安装包。

### 第 0.5 步执行方式（需本人授权）

1. 先确认这台机器上登录的是**测试小号**；若仍是本人主号，注入的封号风险必须由本人明确承担后才继续。
2. 授权安装 C++ 生成工具 + CMake + vcpkg（体积大、需管理员权限，装在主力机上）。
3. 按 **x86** 配置从 `dev-3.9.11.19` 源码编译 `wxhelper.dll` 与注入器，记录源码 commit SHA 与构建参数。
4. 注入后**先只调用"检查是否登录"接口**（不 hook、不发送），观察是否崩溃——用最小动作取得"偏移是否兼容"的答案。
5. 成功 → 进入只接收 spike；失败（崩溃／404／完全无响应）→ 立即卸载注入并停止，回到"换客户端版本"或"换路线"的决策；**不做偏移移植**，除非单独授权（那是逆向工程的独立工作量）。

### 第 0 步执行方式（一次会话，约 30–60 分钟，需本人到场）

1. 准备**独立 Windows 环境**（备用机／虚拟机／Windows 云主机），不要用主力机；也避免主力微信被牵连。
2. 取得 3.9.x 客户端安装包：官方渠道已不再下发旧版，来源可信度本身是本次风险之一 → **必须先记录来源与安装包 SHA-256**，来源不可信就中止。
3. 本人到场，用**测试小号**扫码登录（测试小号需已加知情测试好友）。
4. 判定：
   - **能登录、放置观察后不掉线** → 通过，进入第 1 步；
   - **提示版本过低 / 被强制升级 / 登录后很快掉线** → 路线不成立，停止，回到路线决策；
   - 任何"账号被限制"的提示 → 立即停止并记录。

## 1. 若第 0 步通过：只接收 spike（与 QQ 同等级）

沿用 QQ 的方式，不自创流程：

- 注入 `wxhelper.dll` 后，只调用 `hook消息`（必要时 `hook图片`／`hook语音`），把事件 POST 到本机 **apps/bridge 形态的新适配器**；原始报文按现状做法**私密落盘**，只把去敏事实写进证据。
- 收件人只用知情测试好友，各类型各一条：文字、图片、语音、表情。
- 只接收阶段**不开自动发送**；本人手发一条用于判定"本人/系统回显能否区分"。
- 记录三族结论（收/发/回执）与三族 unknown（回显信号、历史补齐、媒体完整性），并生成微信版报告与快照。

## 2. 需要新写的适配器（有界工作量）

- 新包 `packages/platform/wechat`：入站校验 + wire→公共事件归一化 + 出站；出站必须仍只经 02 的 `withDispatchLease`，桥接自身不持发送授权（与 [decisions.md](../decisions.md) A16 同一套约束）。
- 已从上游源码确认的入站报文形状（`app/wxhelper/src/sync_msg_hook.cc`）：JSON 含 `pid`、`fromUser`、`toUser`、`content`、`signature`、`msgId`、`msgSequence`、`createTime`、`displayFullContent`、`type`；图片消息额外带 `base64Img`。→ **有平台消息 ID**，这是它相对 UI 自动化路线的关键优势。
- 已知接口面（README 功能表）：检查登录、发文本／图片／文件、hook 消息／图片／语音、获取消息附件与 silk3 语音、联系人列表、撤回消息；默认 HTTP 端口 19088，hook 类接口须先调用对应 hook 才会推送。
- 预计回执上限：hook 给得到平台消息 ID，但**没有 delivered 级证据**，因此大概率与 QQ 同为 `accepted` 级。

## 3. 需要本人确认的冲突点

- **封号风险**：注入 DLL 修改客户端内存，风险高于 QQ 桥接，只能用于测试小号。
- **用途声明**：仓库有 MIT 许可文件，但 README 声明"仅学习研究、勿商用"。本项目自用，仍要本人明确接受。
- **常开 Windows 宿主**：与 [aliyun-readiness.md](aliyun-readiness.md) 的 Linux 规划、以及 AC23"关机后仍持续运行"都要重新对齐（自带机器长期开机或 Windows 云主机）。
- **版本债**：腾讯每次升级都可能让 hook 失效，恢复要靠重新逆向（上游 wiki 的 Ghidra 脚本流程就是为此而写）。

## 4. 中止条件

- 第 0.5 步发现偏移不兼容（崩溃或接口全 404），且本人不接受偏移移植或换客户端版本；
- 第 0 步出现除"能稳定登录"以外的任何结果；
- 出现账号被限制／封禁的任何提示；
- 安装包来源无法记录可信哈希；
- 上游 issue 在这期间出现"3.9.x 已完全无法登录"的确认，且没有可用替代分支。
