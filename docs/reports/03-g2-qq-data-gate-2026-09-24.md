## G2 数据边界结论

1. 入站原始字节先进入私有文件与 `platform_inbox_raw`，接受事件的 outbox 先提交；随后 02 在自己的事务里调用 03 provider 写消息、失效旧快照、更新 epoch 和控制。重复同一平台键不会再次运行 02。`provenance.rawEventRef` 是 `bridge:{accountId}:{sha256 前 32 位}`，可与原始记录的完整 `payload_sha256` 核对；它不是 `payload_ref` 文件路径，消费方不能把它当路径读取。
2. provider 的联系人查询隔离、事实来源拒绝规则与受限角色 RLS 用例通过。未登记对端只保留最小发现元数据，无任务/无发送；相同键冲突的重放不会留下第二个原始文件。新门禁固定已登记联系人重放和控制状态不变式。
3. 对端不可审计的自身账号消息现在保留在受限 `unmapped:self` 原始事件范围并暂停该账号的会话；没有绑定联系人时不猜出 `data_messages`。03 provider 若收到可信路径传来的 `unknown`，会保留来源且拒绝其产出本人事实；Owner 只读投影安全展示引用。02/06 已收到 `listUnknownOrigins` 调用契约；当前是否合并到 Owner API 由其专项验证。

## 需要总控协调的接口提案与缺口

**G2-03-A，01 的自身消息对端映射。** 当前 01 已把无法映射的自身消息保存为受限 raw，并让 02 暂停该账号下会话，避免猜成联系人。经审计的对端映射仍待真实平台能力/证据，届时再联测 `PlatformSelfMessageUnattributed -> actor=unknown -> PAUSED_OWNER`；不信任事件自身 `target_id` 猜测对端。

**G2-03-B，平台撤回/编辑证据失效。** 总控已接受 A19，分配 0008 审计迁移；03 `invalidatePlatformMessage` 与 02 同事务消费、07 平台变更用例和 fake OneBot recall 用例均通过。精确定位、墓碑、事实/分析/快照失效、epoch/outbox 与匹配失败暂停已覆盖。D09 的真实平台编辑正文语义仍未验证，编辑新正文不会自动进入上下文。详见 `03-platform-mutation-port-proposal-2026-09-24.md`。

**G2-03-C，原始文件生命周期。** 01 已在同一平台键冲突检查后才写私有文件，fake OneBot 用例证明冲突重放不会留下第二份孤儿文件。D07 未定前，不声称所有异常回滚路径、物理媒体/原始文件或备份清除完成。

**G2-03-D，`PlatformOriginResolved` 持久化提案。** 现有 `data_messages` 只有可变 `actor`、`version` 和原始 `provenance`；没有来源更正的独立证据与旧值审计表。建议总控分配 0008 之后的新迁移编号，新增只追加的来源更正记录，含 `message_id/contact_id/from_actor/to_actor/evidence_refs/old_version/new_version/event_id/resolved_at`，RLS 按 contact_id，唯一事件键做重放去重。03 provider 在 02 消费同一事务内锁定原消息，只允许 `unknown -> owner|agent` 且要求可验证的证据引用，追加更正审计、提升消息版本、失效依赖事实/分析/快照、提升 dependency epoch 并写 outbox；02 同事务失效未提交计划，保留 `OWNER_ORIGIN` 暂停直至显式恢复。不能直接覆盖原始 unknown 证据，也不能因更正自动解除暂停。需总控先明确 01 事件证据格式和公共接口，再写该事项的迁移与实现。

D05 无真实历史样本，导入仍限预览/去重，不解析未知格式。D07 的媒体与原始事件文件、备份清除周期及执行机制仍待总控决定；数据库墓碑不能代替物理清除。
