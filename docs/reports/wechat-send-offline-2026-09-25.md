# 微信发送可行性：离线门禁

日期：2026-09-25。只读检查本机 `WeChatWin.dll` 3.9.11.25，SHA-256 `2058A926258BAEAECF92B30668FF200382F4493B0A5323428781D0B993E19C51`；没有调用微信发送接口，也没有向任何人发送消息。

## 已确认

- 当前移植的 wxhelper DLL 只校准了接收和登录检查两个偏移。上游 `kSendTextMsg=0x22c2010` 落在函数体中部，起始指令为 `movaps [rax-0x48],xmm6`，不是可调用入口；`kGetSendMessageMgr=0x1b4f500` 和 `kFreeChatMsg=0x1b50d80` 也不是可靠入口。三者都不得在本机客户端上调用。
- 源码 `WeChatService::SendTextMsg` 调用内部 `send` 后，把返回值存入 `success`，随后固定 `return 0`。HTTP `/api/sendTextMsg` 因而可能报告 `code:0`，即使内部结果不是成功；该响应不能作为受理回执。
- 二进制包含 `SendMessageMgr::sendTextMsg` 字符串，但现有只读定位器没有找到对该字符串的直接引用；用其它函数的版本差值推测入口缺乏足够依据。本轮不填猜测偏移。

## 工程准备

新增独立的 `wxhelper-send-port.mts` 候选端口，只用于注入的假传输测试。它核对账号、授权对象、真人确认前置检查、方案时限和纯文本长度；一次提交后无论 HTTP 报什么，都返回 `RESULT_UNKNOWN`，不自动重试。正式微信桥接仍只接收，未导入该端口，也没有发送 worker。

本机单元测试通过；隔离 PostgreSQL 真实事务测试也通过：两段文字经 02 确认后，假接口第 1 段返回 `code:0`，发送账本仍记 `RESULT_UNKNOWN`，第 2 段在发送前取消，联系人因 `UNKNOWN_SEND` 暂停；假接口只收到 1 次调用。这个结果证明本地门禁行为，不代表微信平台已经发送或受理。

完整本机门禁 `npm run verify` 通过：216 unit、9 contract、28 PostgreSQL integration、13 E2E，加网页构建，0 fail、0 skip；日志私留 `.local-wechat-spike/verify-send-offline-20260925.log`。

## 第一轮检查时的下一门槛

1. 在同一 SHA-256 的离线二进制上，分别确认发送、管理器获取和消息释放的真实函数入口与调用约定，并修正 wxhelper 固定返回 0 的问题，重建后只用假接口核对响应语义。
2. 补齐真实平台回执语义后，用隔离 PostgreSQL 和假传输复测受理与失败分支；当前未知结果暂停分支已通过。
3. 以上通过后，再明确一次真实测试的收件人、原文和次数，由本人逐条授权；出现未知结果立即停止并人工核对。

第一轮结论：**离线发送门禁未通过，真实微信出站继续关闭**。下方记录继续核验的结果。

## 追加核验：三个函数入口已定位（2026-09-25）

对同一 SHA-256 的本机 `WeChatWin.dll` 继续只读反汇编，定位到以下入口；上面的旧偏移仍然是错误的。

| 作用 | 本机入口 RVA | 独立证据 |
| --- | --- | --- |
| 获取发送管理器 | `0x1b53fd0` | `int3` 填充后有完整函数序言；内部调用 `SendMessageMgr` 构造函数 `0x22b72d0`，将单例保存并返回；59 处直接调用候选。 |
| 通用消息发送 | `0x22c6b60` | `int3` 填充后有完整函数序言，读取前四个寄存器参数和后续栈参数；函数体包含 `SendMessageMgr::sendMsg` 日志引用，31 处直接调用候选。 |
| 释放聊天消息对象 | `0x1b55850` | `int3` 填充后有完整函数序言；初始化析构虚表并清理对象字段；与发送调用紧邻出现。 |

关键的交叉调用点在 `0x1b5a0b5` → `0x1b5a0e4` → `0x1b5a0f0`：依次取管理器、按 wxhelper 原有 8 参数布局调用 `sendMsg`、对同一 `ChatMsg` 地址调用析构函数。另一调用点 `0x1b519ca` → `0x1b519d3` 也把发送和析构连续配对。三个入口的旧/新地址差值彼此一致（管理器和析构均为 `+0x4ad0`，发送为 `+0x4b50`）；交叉调用和函数序言才是采用它们的主要依据。

发送函数的退出路径在 `0x22c77bd` 把第一个参数（`ChatMsg` 地址）放入 `rax` 后返回。因此原 wxhelper 保存的 `success` 实际是对象指针，既不是微信消息 ID，也不是受理状态；固定返回 0 的旧包装确实会制造假成功。

已在 gitignored 的本地 wxhelper 源码副本中仅更新 `V_3_9_11_25` 的三个偏移，并让 `/api/sendTextMsg` 在函数调用返回后给出 `code:2, msg:result_unknown`；发送日志不再记录收件人和正文。离线 MSVC Release x64 构建成功，产物留在 `.local-wxhelper/wxhelper-build-391125/app/wxhelper/lib/Release/wxhelper.dll`，SHA-256 `9F1A96D9E51738F62E0926845DEC274074999EDA9A174867D7507B52A7EBEB3D`。此前只接收实测的 DLL 哈希仍是 `F67EFF42…`，未被替换；本轮没有启动或注入微信，也没有调用发送接口。

仓库新增只读的 `scripts/wechat-send-binary-preflight.mts`：在任何后续实测前，可对客户端文件核对固定 SHA-256、三个入口序言、同一调用链和返回指令。本机对安装文件运行通过；换版本或字节变化会直接拒绝。假传输候选端口的 4 项单元测试也通过，正式桥接仍未导入它。

**门禁状态**：三个入口及原调用约定的离线证据已足够进入受控验证，但没有平台受理回执，不能把 HTTP 返回当成功。正式桥接仍只接收；下一步需在测试号登录后单次验证新 DLL 的安全性和一条经本人明确授权的测试消息，并把回显与私有发送账本对照。出现超时或未知结果时不自动重发。

## 本机登录检查尝试与审批边界

本人完成测试号登录后，本机出现两个独立的 `WeChat.exe` 进程。首次把新版 DLL 加载到较早的未登录窗口进程，只调用 `/api/checkLogin`，得到 `code:0`；进程未崩溃。随后通过只读内存标志确认另一个进程才是已登录会话，关闭多余的未登录进程；已登录进程持续运行。

向已登录进程加载新版 DLL 的动作被系统自动审批拒绝：它认为该动作会修改正在使用的客户端，有崩溃或不安全行为风险，而当前用户授权只覆盖登录，没有明确覆盖这次注入。**没有绕过拒绝，也没有把 DLL 加载到已登录进程**。最终状态：测试客户端仍运行，已登录进程无 wxhelper DLL，本轮微信发送接口调用 0、消息发送 0。后续要继续此实测，需本人明确同意在测试号已登录进程上加载此哈希的 DLL；真实发送仍需另行确认收件人、原文和次数。
