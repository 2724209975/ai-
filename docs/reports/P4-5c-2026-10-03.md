## 句柄来源与受限取值方案

5 个全局位置均属于可写 `.data` 的虚拟零填充区域，磁盘没有对应原始字节。这在 PE 中并非异常，但只能证明位置映射，不能证明运行时值或对象类型。

| 全局 | RVA | 旧取值路径 / 问题 |
| --- | --- | --- |
| kGPInstance | `0x58dd300` | 根指针 + 27 个固定 storage 偏移；直接解引用 handle `+0x50`、名称指针 `+0x78`、长度 `+0x80` |
| kMultiDBMgr | `0x593abf8` | 根 → 数组 `+0x50`、数量 `+0x68` → 每个 DB 对象；数量无上限 |
| kPublicMsgMgr | `0x5938198` | 根 → 3 个 storage；不是本卡所需来源 |
| kFavoriteStorageMgr | `0x593b790` | 多层裸指针；不是本卡所需来源 |
| kHardLinkMgr | `0x593ab28` | 多层裸指针 → 6 个 storage；不是本卡所需来源 |

唯一值得继续定位的候选是 MultiDBMgr 的 DB 对象 `+0x20` → BufInfoStorage，再经 `+0x50/+0x78/+0x80` 取得句柄/名称/长度。**这是旧源码候选布局，不是当前客户端已确认的 MediaMSG 来源。** 旧代码会对每个库调用 `sqlite3_exec` 扫 `sqlite_master`；根指针、范围、名称长度、数量及生命周期均未验证。helper 自己的 recursive_mutex 只保护自身容器，不能证明微信对象不会同时销毁/关闭。

后续方案的准入条件：

1. 先离线定位真实 SQLite prepare/step/column/finalize 入口，以多个已解码调用点、控制流、参数/返回值及展开范围交叉证明身份与 ABI；每个偏移绑定固定客户端完整指纹。不得将本表“最近起点”直接改成新偏移。
2. 通过客户端创建/注册/关闭的调用链证明 BufInfoStorage 与 MediaMSG 的归属、字符串编码/长度、锁与生命周期；若只能证明地址可读，仍拒绝接入。
3. 独立受限接收版本仅收集证明后的 MediaMSG 句柄，最多 64 个去重，拒绝溢出、空指针、无界名称/数组、未知存储和变化中的快照；不复用旧全库 schema 扫描，不公开 SQL/db handle 参数。真正的平台锁/生命周期机制未确认前，不实现取值。
4. 仅允许当前绑定好友接收事件的精确字符串 MsgSvrID，沿用 P4-5a 固定参数查询、唯一 BLOB、2 MiB 上限、失败关闭/finalize；真实 schema 必须另外验收。新补丁/接口/产物先审定，仍不改生产允许指纹。
5. 完成离线证据和独立构建后，再准备本人执行的一次接收/字节核对清单；AI 不执行平台操作。Silk 容器/转码/ASR 是后续卡，不因拿到任意 BLOB 就宣称语音可理解。
