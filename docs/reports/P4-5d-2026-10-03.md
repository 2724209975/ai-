# P4-5d SQLite 入口与 MediaMSG 来源离线定位

本卡范围内的工作**部分完成**：四个离线只读工具已建成并带回归夹具（共 34 项新测试），固定客户端里嵌的数据库引擎身份已确认，15 个锚点字符串与 22 处代码引用已产出可重复证据，并确认了两条结构性事实——**镜像里存在无人引用的 SQLite 区域**，以及**10 个登记的 SQLite 偏移有 9 个不是函数入口**。**但 SQLite 入口的函数身份与 ABI 尚未证明，MediaMSG/BufInfoStorage 来源没有取得任何证据**，因此结论仍是 **NO_GO**，`voiceDatabaseReady=false` 不变。

本轮只读磁盘文件；未启动、注入或卸载 helper，未读取真实进程内存或聊天数据库，未调用平台或模型，未修改登记源码/偏移、构建产物或生产指纹，无新增迁移或依赖。范围见 [审定](P4-5d-proposal-2026-10-03.md)。

## 结论先行

1. **固定客户端嵌的是 SQLCipher 4.2.0（打包 SQLite 3.28.0），不是普通 SQLite。** 版本由三条独立证据唯一确定：版本串 `"3.28.0"`(`0x4d9bc54`)、`sqlite3_libversion()`(`0x3a99930`，7 字节叶子函数)、`sqlite3_libversion_number()`(`0x3a99940`，返回 `0x2e3420`=3028000)。同一字符串带内还能读到 `PRAGMA cipher_compatibility`、`HMAC verification failed for page %d`、`aes-256-cbc`、`OpenSSL 1.1.1l  24 Aug 2021`、`SELECT sqlcipher_export('migrate')`。这解释了两件事：为什么历史偏移难以与上游 SQLite 对上；以及为什么**页面级**证据（`SQLite format 3` 头）不能证明能直接读库——库是加密的。
2. **15 个锚点全部在 P4-5c 记录的 RVA 上逐字节验证通过**，并在可执行节中定位到 22 处 RIP 相对引用（明细见[证据 JSON](P4-5d-evidence-2026-10-03.json)）。工具因此可以在**不改指纹、不读进程**的前提下重复产出引用证据。
3. **镜像中存在一块无人引用的 SQLite 代码/数据。** `sqlite3_get_table_cb` 的函数体已定位（入口 `0x3a74925`，见下），但全图范围内**没有任何代码加载它的地址，数据节里也没有任何 8 字节指针槽持有它**；`sqlite3_get_table()` 的错误字符串同样零引用。这是一条对后续所有偏移工作都有影响的结构性事实。
4. **10 个登记的 SQLite 偏移有 9 个不是函数入口。** 它们都落在异常目录范围的**内部**（距起点 `+0x20` 至 `+0x900`），自身**没有任何函数序言字节**，也没有蹦床可以解释；`exec` 更是在字节层面被证明落在一条 7 字节指令的第 4 个字节（disp32 中间）。只有 `finalize` 结构上像个入口，而 P4-5c 已发现它 ABI 不相容。这条结论**只否决既有登记，不给出新偏移**。
5. **找到并验证了两个真实入口，而且它们不来自任何地址表。** 方法是从调用点反推（列访问配对），再用结构事实（异常目录范围起点 + 序言字节）与真实调用点验证：`0x3a6d90`（**64** 个调用点）与它内部调用的 `0x3a64b0`（**104** 个调用点）。调用点还直接给出 ABI：`{RCX=stmt, EDX=iCol, R8=, R9=pOut}`、返回布尔、第 4 参数指向 SQLite `Column` 结构。与之对照，登记的 `k_sqlite3_exec`=`0x3a59b30` 直接调用点为 **0**。**这条证据证明新方法可行，但没有证明它们对应源码里哪两个函数，也没有给出其余 9 个偏移的正确入口。**
6. **入口 ABI 仍未整体成立。** 已定位的 SQLite 内部字符串引用点不构成指向 `k_sqlite3_exec`/`prepare` 的调用链；除上面两个入口外没有第三个入口有 ABI 证据。按审定要求，**不因"找到了引用点"就放行**。
7. **操作码名表这条路走不通（已留证）。** 全图唯一的 `Init` 与其余操作码名相距很远，按连续段检测只得两段且都不以 `Init` 开头，因此工具拒绝输出任何操作码编号——这挡住了一条原本可能被误用的版本指纹路径。
8. **MediaMSG/BufInfoStorage 来源证据为零**，本轮没有产出任何可用于该目标的结果。

## 交付物

### `scripts/wxhelper-db-entry-scan.mts`（离线引用扫描器）

在可执行节中定位"计算出的目标等于给定 RVA"的 x86-64 RIP 相对寻址指令。x86-64 下 RIP 相对寻址的判据就是 modrm `mod=00, rm=101`，即 `(modrm & 0xc7) === 0x05`；覆盖 `lea`、`mov` 读写、`movzx/movsx`、`cmp`、`test`、`movss/movsd`、`movaps`、`movdqa`。

边界与诚实性约束，都写进了文件头注释：

- 这是一个**单一寻址形式的受限解码器，不是通用反汇编器**，且**不做控制流分析**：报告出的位置是"这种指令可能从这里开始"，因此每个用作证据的位置都必须用独立反汇编器（`wxdisasm`）在其精确 RVA 上复核。
- 不执行代码、不访问进程、不跑 SQL、不提升任何偏移。
- 越界读取、错位节表、非 PE32+/非 x64、超限文件全部以固定错误码失败，错误文本不含路径或文件内容。

### `scripts/wxhelper-db-entry-scan.test.mts`（回归夹具，17 项）

这个夹具不是形式主义，它**抓到了三个真实缺陷**：

| 缺陷 | 表现 | 根因 |
| --- | --- | --- |
| modrm 掩码比较写反 | 对**任何**目标都报 0 处引用 | 写成 `(modrm & 0xf8) === 0xf8`，要求 mod 位为 `11`（寄存器寻址），自相矛盾。正确判据是 `(modrm & 0xc7) === 0x05` |
| REX 备选被当成顺序字节 | 所有带 REX 前缀的指令全部漏检 | `prefix: [0x48, 0x4c]` 被实现为"先匹配 0x48 再匹配 0x4c"，等于要求 `48 4c`，永远匹配不上。备选必须展开成各自独立的形状 |
| 只覆盖 REX `0x48/0x4c` | 含 REX.B 的 `lea/mov` 用 `0x49/0x4d` 编码时漏检 | MSVC 可为任意寄存器选择置位 REX.B。已扩到四种 REX 组合，并对展开后的形状**按 `(op, prefix, opcode)` 去重**，否则同一字节序列会被匹配 4 次、引用数虚高 4 倍 |

**前两个缺陷都会让"没有引用"看起来像一个真实结论。** 我在修正前差点把一次工具故障（全 0 命中）当成"编译器把字符串放进了指针表"的发现——是跑了已知必有命中的对照才发现方向错了。这也是为什么第三个缺陷必须由显式用例锁住：夹具现有 17 项，含 12 种真实指令编码、目标不匹配、`mod=01` 与 SIB 负例、非可执行节不入选、畸形镜像失败关闭。编码案例的期望值按 Intel 手册写定（`89 05` 是 32 位无 REX.W，`48 89 05` 才是 64 位）。

### `scripts/wxhelper-db-xref-audit.mts`（锚点引用审计驱动）

1. 先核对**整图 SHA-256** 是否等于登记构建，指纹不符直接拒绝解释任何偏移；
2. 再核对每个锚点字符串**真的**位于记录的 RVA 上（版本变化不会让锚点静默漂移）；
3. 扫描可执行节，报告每处引用的精确位置、指令类型、位移、解码目标与**原始指令字节**，供独立复核。

输出为固定协议 `p4-5d-xref-audit-v1` 的 JSON，只含哈希、RVA、指令字节与库内字符串文本，不含磁盘路径、身份、聊天内容或内存转储。`disposition` 恒为 `NO_GO`：审计成功表示"证据已产出"，**不表示运行获准**。

用法：

```powershell
node scripts/wxhelper-db-xref-audit.mts <固定客户端DLL> <登记offset.h> --json-out <path>
```

### `scripts/wxhelper-db-entry-structure.mts` + 夹具（10 项）

回答一个此前一直靠假设带过的问题：**登记的 `k_sqlite3_*` 偏移，在固定客户端里到底是不是函数入口？** 每项偏移只看磁盘就能得到的证据：

1. Windows x64 异常目录（`.pdata` / `RUNTIME_FUNCTION` 数组）：只有范围起点才可能是入口，**落在范围内部的偏移一定不是**；
2. 偏移自身与其所在范围起点的**序言字节形状**（`mov [rsp+d],reg`、`mov rax,rsp`、`push r12`、`sub rsp,imm8` 等 14 种 MSVC x64 形状）；
3. 范围起点是否为 `jmp rel32/rel8` **蹦床**（若跳到该偏移，说明偏移是真实实现而起点只是跳板）。

它**刻意不做"字节→入口"的判定器**：MSVC 会把多个函数合并进同一个展开范围，所以范围起点是必要证据而非充分证据。工具只报告观测到的事实，并**拒绝把任何偏移称为已验证入口**。它不执行代码、不访问进程、不跑 SQL、不提升偏移。

用法与结果：

```powershell
node scripts/wxhelper-db-entry-structure.mts <固定客户端DLL> <登记offset.h> --json-out <path>
```

| 项 | 值 |
| --- | ---: |
| 异常目录范围数 | 182,927 |
| 记录偏移中位于范围**内部**的 | **9 / 10** |
| 记录偏移中位于范围起点的 | 1 / 10（仅 `finalize`） |
| **自身带函数序言字节的偏移** | **1 / 10** |
| 结构上可判为入口的偏移 | **1**（`finalize`，且 P4-5c 已指出其 ABI 不相容） |

### `scripts/wxhelper-string-xref.mts` + 夹具（7 项）

第三个工具，用来回答"某个字符串在哪里被引用"——不限于 SQLite 内部锚点。给一个字符串，它报告：

- ASCII 与 UTF-16LE 两种编码**各自**出现在哪些 RVA、落在哪个节，并附上可打印的上下文字面量（尾随 NUL 会被去掉，不算内容）；
- 每一处出现被可执行节中哪些 RIP 相对指令引用，附精确位置与原始指令字节；
- 没有引用的出现照样报告，计数为 0——**"零引用"是结论，不是缺失**。

它是后续卡"从应用侧字符串括出活代码边界"的直接工具（本轮的数据库文件名尝试见下）。工具不执行代码、不访问进程、不跑 SQL、不提升偏移。

```powershell
node scripts/wxhelper-string-xref.mts <固定客户端DLL> <字符串> [<字符串>...] [--json-out <path>]
```

### `scripts/wxhelper-db-entry-candidates.mts` + 夹具（9 项）

**本卡最关键的工具**，也是唯一真正推进了"入口身份"这条线的工具。登记的偏移已被证明不是入口，所以它**不信任任何地址表**，改从**调用点行为**反推入口候选：

- `sqlite3_column_blob(stmt,i)` 与 `sqlite3_column_bytes(stmt,i)` 是取 BLOB 列的标准配对，调用方会把**同一个列号**传给两个不同函数。在 x64 ABI 下这必然留下 `mov edx,<小立即数>; call T` 与 `mov edx,<同立即数>; call U`（`U != T`）；
- 工具扫描全图，按"两个不同目标反复收到同一个立即数列号"聚出候选对；
- 每个候选都附带独立的结构事实：异常目录范围起点、序言字节形状、**直接调用点数量与位置**。

它同样只读磁盘、不执行代码、不提升偏移，并且 `disposition` 恒为 `NO_GO`。

**方法论局限必须说清**：重复列号这个信号本身**噪声很大**——`0x883d0` 有 724 个调用者，它显然不是列访问器，只是碰巧也收 `edx` 立即数。所以工具输出的是**候选**，不是结论；真正起作用的是"启发式找候选 + 再用结构事实与调用点逐个验证"。本卡据此只确认了**一个**入口（见下）。

### `scripts/wxhelper-db-entry-verify.mts` + 夹具（7 项）

第四轮的收口工具，把上一轮**手工**做的入口验证固化成可重复检查。给定候选地址，报告：

1. 结构事实（异常目录范围起点、序言形状、是否文件内有字节）；
2. **序言原始字节**（32 字节），让入口是"看得见"的而不是推出来的；
3. 每一个直接 `call rel32` 调用点，连同其**前 24 字节 / 后 12 字节**，使每个调用点的参数准备可直接判读；
4. 判定 `entryLike` = 范围起点 + 有序言 + 有调用者，三者缺一不可。

在固定镜像上的实测：

| 地址 | entryLike | 范围起点 | 直接调用点 | 序言 |
| --- | --- | --- | ---: | --- |
| `0x3a6d90`（调用点反推） | **是** | 是 | **64** | `push r15` |
| `0x3a64b0`（`0x3a6d90` 内部调用的子函数） | **是** | 是 | **104** | `push r15` |
| `0x3a59b30`（**登记**的 `k_sqlite3_exec`） | 否 | 否 | **0** | 无 |
| `0x3a1cbe0`（**登记**的 `k_sqlite3_finalize`） | 是 | 是 | 82 | `mov [rsp+d],reg` |
| `0x3a7509`（一个调用点） | 否 | 否 | 0 | 无 |

**新增一条独立发现**：`0x3a6d90` 内部调用的 `0x3a64b0` 本身也是范围起点 + 序言 + **104 个调用点**——也就是说，顺着"从调用点反推"这条链，已经落到库的核心列取值辅助函数之一上。

### `scripts/wxhelper-sqlite-version.mts` + 夹具（8 项）

**本卡最有价值的一条发现**：内嵌引擎的版本被**唯一确定**为 **SQLite 3.28.0**（即 SQLCipher 4.2.0 的打包版本）。三条独立证据互相印证：

| 证据 | 地址 | 机器码 | 说明 |
| --- | --- | --- | --- |
| 版本字符串 | `0x4d9bc54`（`.rdata`） | `"3.28.0"` | 全图唯一的合理版本串 |
| `sqlite3_libversion()` | `0x3a99930` | `48 8d 05 … c3` | `lea rax,[rip+…]; ret` —— 返回版本串指针 |
| `sqlite3_libversion_number()` | `0x3a99940` | `b8 20 34 2e 00 c3` | `mov eax,0x2e3420; ret`，`0x2e3420` = **3028000** = 3×1000000+28×1000 |

`sqlite3_libversion()` 是一个**只有 7 字节的叶子函数**（无栈帧），这是 SQLite 上游的写法；`sqlite3_libversion_number()` 返回的立即数按 SQLite 的 `SQLITE_VERSION_NUMBER` 公式恰好等于版本号。三条同时对上的概率可以忽略。

工具**要求三条同时成立才报版本**——只有字符串、或只有数字，都会拒绝；数字与字符串不一致也拒绝；`3.99.0` 这类不合理组合按巧合字节拒绝。夹具把这四条规则全部锁住。

**为什么这条发现重要**：此前所有"这个地址是 `sqlite3_prepare`"式的判断，都缺少一个可对照的上游基准；登记偏移之所以能一路被误用，正是因为没人确定过版本。现在有了 3.28.0，正确入口可以用**确定性**方式求出——对着该版本的 `sqlite3.c` 比对函数体与调用约定，而不是靠猜偏移。

**这同时暴露了登记偏移的又一层问题**：P4-5c 记录的那批偏移（含 `k_sqlite3_exec`）与真实 3.28.0 API 入口完全对不上；本轮新识别的三个入口（`0x3a99930`/`0x3a99940`/`0x3a99950`）才是经得起复核的地址。

### `scripts/wxhelper-vdbe-opcodes.mts` + 夹具（9 项）

第五个工具，本意是读 VDBE 操作码名表，把库内 `cmp <opcode>, imm` 里的常量翻译成真实操作码，顺便用操作码集合给 SQLite 版本做指纹。

**结论：在固定客户端上取不到完整表，工具如实报告失败而不是猜。** 探查结果：`Goto`(`0x519bde8`)、`Transaction`(`0x519bc70`)、`Explain`(`0x519c480`)、`Abortable`(`0x519c470`) 同处一区，但全图唯一的 `Init` 在 `0x50c6974`，相距很远；按连续标识符段检测只得到两段（141 项与 53 项），**都不以 `Init` 开头**。因此工具**拒绝输出任何操作码编号**，只报告"检测到的候选段"与"为何不编号"。

过程中的一个真缺陷值得记下：客户端把每个名字**填充到定宽**，名字之间是 NUL 填充，产生了空字符串 token；我最初的段检测把空 token 当分隔符，于是每个名字都被切成独立段（表现是"一段都没有"）。修法是明确区分"空 token（填充，不切段）"与"非标识符文本（切段）"，并由夹具锁住。

这个工具目前**没有产出结论**，它的价值是：把"这条版本指纹路走不通"变成了有据可查的结论，并留下了可复用的段检测器。

### `scripts/wxhelper-string-map.mts` + 夹具（10 项）

第八个工具。因为内嵌引擎**不导出任何符号**，唯一能在这 100 MB 里导航的办法就是**看每段代码引用了哪些字符串**。给一个代码 RVA 区间，它报告区间内代码引用的每一个不同字符串字面量、引用次数、精确位置，以及**每个位置所属的函数范围**（异常目录）。

在固定镜像 `0x3a20000`–`0x3a40000`（库的 SQL 编译器区）的实测：141 个不同字符串。几条有直接价值的归属：

| 字符串 | 次数 | 落在哪些函数 |
| --- | ---: | --- |
| `%s at line %d of [%.10s]` | 12 | `0x3a20ae0`、`0x3a21369`、`0x3a215d0` |
| `misuse` | 6 | `0x3a21e50`、`0x3a22da0`、`0x3a24060` |
| `API called with finalized prepared statement` | 4 | `0x3a21e50`、`0x3a22da0`、`0x3a24060` |
| `database corruption` | 6 | `0x3a20ae0`、`0x3a21369`、`0x3a215d0` |
| `string or blob too big` | 3 | `0x3a22a50`、`0x3a25810` |

**`misuse` 与 `API called with finalized prepared statement` 同时落在同样的三个地址上**，这不是巧合：它们就是 SQLite 里检查 `pStmt->db` 的那两个分支。反汇编 `0x3a22da0` 可以直接读出结构：

```text
03a22da0  40 53                    push rbx
03a22da2  41 55                    push r13
03a22da4  41 57                    push r15
03a22da6  48 81 ec 90 01 00 00     sub rsp, 0x190
03a22db0  48 8b d9                 mov rbx, rcx            ; 语句指针在第 1 参数
03a22db6  48 85 c9                 test rcx, rcx
03a22db9  75 09                    jne 0x3a22dc4
03a22dbb  48 8d 15 e6 c0 77 01     lea rdx, [rip+…]        ; ->0x519eea8「API called with NULL prepared statement」
```

### `scripts/wxhelper-column-family.mts` + 夹具（7 项）

第九个工具，也是本轮**真正推进"列访问族"这条线**的工具。推导链条：

### 该回调与其调用者是死代码（结构性发现）

在定位到 `0x3a74925` 后，我反查了"谁引用它"：

| 检查 | 方法 | 结果 |
| --- | --- | --- |
| `call rel32` 指向该地址 | 扫描可执行节的 `E8` | 0 |
| RIP 相对 `lea/mov` 取该地址 | 扫描可执行节（含四种 REX 组合） | 0 |
| 数据节中的绝对 VA 指针槽（`0x183a74925`） | 在非可执行节逐字节找 8 字节小端值 | 0 |

**第三条不依赖任何指令解码器**：它只比较字节，所以"零"不受我前述解码缺陷影响。三条同时为零，结论是：`sqlite3_get_table_cb` 在本镜像中**没有被任何代码或数据引用**，因此创建并使用它的 `sqlite3_get_table()` 同样不可达。

这与 7 个零引用锚点指向同一机制：链接器保留了整个 SQLite/SQLCipher 目标文件（连 `sqlite3_errstr()` 的错误文本数组、`xCallback` 这类调试字符串都留着，`API called with finalized prepared statement` 有 88 处引用），但**没有做未使用函数的裁剪**。对后续偏移工作的含义很直接：**"某个 SQLite 函数在这里"不等于"它被调用"**，而"这段代码存在"也不能反推某个登记的 k_sqlite3_* 偏移指向它。

### 关于 7 个零引用锚点

`0x519ee90`…`0x51a1ea0` 是一段连续的 SQLite 错误文本数组（NUL 结尾、逐条紧邻）。其中 7 条在可执行节中没有被 RIP 相对访问，**而同区间的相邻条目有明显引用**（`database disk image is malformed` ×1、`interrupted` ×1、`unable to close due to unfinalized state` ×2、`bind on a busy prepared statement` ×27、`API called with finalized prepared statement` ×88）。

为排除工具漏检，我另做了一次**带宽统计**：单遍扫描可执行节，把落在 `0x519d000`–`0x51a3800` 内的 RIP 相对目标全部列出，共 793 个不同目标，覆盖该区间两侧与中间的绝大多数字符串。这证明扫描器在该区间工作正常，7 个零引用是**真实结论**，最可能是这些错误码路径在该构建中确实无人取用（`sqlite3_errstr` 未接或被优化掉）。

**但这是一个可能被误读的结论，我用它做什么、不做什么必须说清**：它**不**支持"这些错误码不可达"或"入口偏移是错的"这类推断，只说明"在本镜像的可执行节里，没有指向这些字符串的 RIP 相对访问"。

| `column_type` | `0x3a1eba0` | 范围内部 | `+0x750` | 无 | 无 |
| `column_name` | `0x3a1ed50` | 范围内部 | `+0x900` | 无 | 无 |
| `finalize` | `0x3a1cbe0` | **范围起点** | — | `mov [rsp+d],reg` | `mov [rsp+d],reg` |

**结论：10 个记录偏移里有 9 个是函数内部的字节位置，而不是函数入口**，且这 9 个自身都没有任何函数序言字节；没有任何一个是蹦床（范围起点没有 `jmp` 指向它们），所以"起点是跳板、偏移才是真实现"这一解释也不成立。

`exec` 可以在**字节层面**独立复核（这也是本轮唯一手工核对到指令级的一项）：

```text
03a59b25  4c 89 a2 b0 00 00 00     mov qword ptr [rdx + 0xb0], r12
03a59b2c  4c 89 a2 b8 00 00 00     mov qword ptr [rdx + 0xb8], r12
03a59b33  c6 82 c0 00 00 00 0b     mov byte ptr [rdx + 0xc0], 0xb
```

记录的 `0x3a59b30` 是 `0x3a59b2c` 那条 7 字节指令的**第 4 个字节**（落在 disp32 中间），既不是指令边界，也不可能是入口。

**这个判定的边界必须说清**：它证明的是"这 9 个偏移不是入口"，**不是**"正确的入口是什么"。异常目录范围起点同样不等于函数入口（MSVC 会做函数合并，多个入口共享一个展开范围），因此它只否决既有登记，不能反向给出新偏移。本卡**没有**据此改任何偏移。

### 一处与本卡无关的不确定断言（已量化，未修改）

`tests/integration/postgres-qq-bridge.test.mts:212` 断言 `two concurrent pumps must claim the committed event once`，实测失败为 `2 !== 1`：两个并发 `tick()` 各自投递了同一条 outbox 事件。**它是非确定性的**——同样的命令、同样的数据库，时而通过时而失败。实测样本：

| 运行方式 | 失败/总数 |
| --- | ---: |
| `node --test tests/integration/*.test.mts` | 8 / 16 |
| `npm run verify`（integration 段） | 8 / 9 |
| 仅该文件 | 0 / 3 |
| `npm run test:integration` | 1 / 4 |
| 含 `--test-concurrency=1` | 0 / 1 |
| 合计 | **17 / 33（52%）** |

**这条断言已是本卡门禁的主要噪声源**：本卡后期多次出现"连续 2–3 次 `npm run verify` 全被它挡下"的情况，而同一批 `unit/app/tools/contracts` 每次都 0 fail。它是既有测试（不在本卡范围），但它让"完整门禁"这件事变得不可靠——建议单独立卡，把断言改成与 `docs/decisions.md` A03 一致的"至少一次"语义，并保留其后的 inbox 幂等断言作为真正的重复抑制验证。

（本卡早先曾依据 3 次单文件通过把它记为"并发负载下的偶发"；随后套件复跑里连续失败，证明该判断不成立，此处按完整样本更正。）

另有一次**一次性**的文件级异常：某一轮 `npm run verify` 里 `tests\integration\postgres-wechat-send-candidate.test.mts` 整个文件报错（不是断言失败）。单独运行该文件通过，随后 4 次套件复跑均未再现，因此记为环境/并行下的一次性事件，**不声称有任何结论**。

判定它**不是产品缺陷**，依据是规格而不是代码注释：

- `docs/contracts.md` 第 115 行：事件通过同库 transactional outbox **至少一次**投递；
- `docs/decisions.md` A03：inbox/outbox **至少一次**，"不宣称 exactly-once"；
- `apps/bridge/outbox-pump.mts` 第 33-34 行也写明第二个 pump 可能重复投递。

机制也吻合：pump 在事务内用 `FOR UPDATE SKIP LOCKED` 选中待发布行后**立刻提交**（锁随即释放），而 `published_at` 是在消费者返回之后才更新。两个并发 `tick()` 因此可以各自读到同一行未发布事件并各投递一次。第 25 行的 `running` 只防**同一个实例**重入，防不住两个实例。

**因此真正不成立的是那条断言**：它按"恰好一次"断言一个明确只承诺"至少一次"的机制，而重复抑制应当由紧随其后的 inbox 幂等断言（第 214-218 行"重复不得再建任务"）来验证。**本卡不改这条测试**：它不在本卡范围内，属需要审定的行为判定；且它同时暴露了一个真实的**未定问题**——pump 目前不保证"两个 pump 恰好一方领取"，若将来要多 pump 并行领取，需要把领取标记放进同一个事务（或引入领取租约），那属于另一张卡。

次要观察（非正确性问题）：`outbox-pump.mts` 第 50 行 `if (!claimed) break;` 在并发下可能让另一次领取多查询一轮（行已被发布，查不到待处理事件），只是浪费一次往返。
