# P2-1 候选反馈采集方案与总控审定

现有 orch_plans 保存原候选和 approved_alternative_id，orch_send_tasks 保存最终确认文字；orch_owner_commands 只有命令 hash，不足以区分拒绝原因和实际展示。重新生成/失效有内部原因，但没有稳定的反馈采集行。

采用既有 data_feedback，一方案一条 candidate:<planId> 记录：先记录 presented，进入 selected/edited/rejected/regenerated/expired 后保留首个终态。shown_alternative_ids 来自网页声明的实际展示，旧客户端没有声明时保持空；rating 只存结构版本、展示/终态时间与失效原因。original_content/final_content 保持 NULL，原候选、选中候选和最终确认文字由联系人范围内的现有表派生，不增加正文副本。确认不等于平台已送达，报告必须另看发送状态。

过期沿用现有 INVALIDATED 语义，包括新来信、暂停、依赖失效等，不新增时间 TTL 或发送判定。重新生成单独记录为 regenerated；已确认的方案后续失效不覆盖其 selected/edited 反馈。不做旧记录回填。

网页增加可选快捷拒绝原因；REST 私有适配增加展示记录与可选 shownAlternativeIds/rejectionReason，继续本人鉴权、CSRF、版本校验；不变更公共发送端口/事件/契约。展示记录不会确认、发送、改版本或扩大权限；动作记录与现有业务事务一起提交，失败则整体回滚。

总控在本人“继续推进”授权内批准本方案，允许当前卡同步维护 docs/development-plan.md 与交付报告。无依赖/迁移变更，0011 仍未分配。数据库 RLS 与联系人/方案绑定必须用真实 PostgreSQL 负测验证；手机 E2E 覆盖可选原因和失败重试。
