## 固定来源和可重复材料

客户端仍为 100,449,384 字节、完整 SHA-256 `2058A926258BAEAECF92B30668FF200382F4493B0A5323428781D0B993E19C51`。CLI 在解释客户端前核对完整指纹，专用解码工具也核对 EXE 指纹 `3C39D1EF5FE2BD56E303941771E01CAD5781743425D39EBD416DBF08266042EA`。只启动磁盘反汇编程序，不加载客户端 DLL。

成功下载了公开 SQLCipher v4.2.0 标签下的 VERSION、vdbeapi.c、vdbeInt.h、prepare.c、main.c、legacy.c，保存到忽略目录 `.local-wxhelper/p45d-upstream/`；下载没有构建、安装或运行上游代码。URL/字节数/完整哈希见 [来源与锚点证据](P4-5d-source-review-2026-10-04.json)。本轮不再继承“拿不到源码，需要本人另给授权”的草稿阻塞；联网只读获取公开对照材料属于本卡工作。

固定客户端的版本串 `3.28.0`、`0x3a99930` 的 `lea rax,<版本串>; ret`、`0x3a99940` 的版本数返回形成交叉证据，结果见 [版本审计](P4-5d-sqlite-version-2026-10-04.json)。检测器已要求真正的 RAX 指针返回形状；普通 RIP 字符串引用不能冒充 libversion。**这支持 SQLite 3.28.0 对照，不足以唯一确定客户端 SQLCipher 的版本或某个真实数据库的加密状态。** 上游标签 VERSION 为 3.28.0，仅说明这份基准适合比较，不能把标签 4.2.0 当成本机身份。[上游 VERSION](https://raw.githubusercontent.com/sqlcipher/sqlcipher/v4.2.0/VERSION)

## 纠正草稿的关键推断

`0x3a24060` 并非已经证明的列读取守卫。其解码行为包括：索引必须从 1 开始、检查 stmt 的 nVar、清理原绑定值并置 NULL、成功时保持锁、失败时解锁并返回 RANGE/MISUSE。这组行为与 `vdbeUnbind` 相符。上游 `columnMem` 则按结果列的零起点索引取值，不能用“出现 finalized/MISUSE 日志”就把二者混为一族。[上游 vdbeapi.c](https://raw.githubusercontent.com/sqlcipher/sqlcipher/v4.2.0/src/vdbeapi.c)

同样，`0x3a24620` 虽只在短序言里复制了 RCX，却把原 EDX 直接传给这个守卫，随后在成功路径释放 mutex、返回守卫状态；它与两参 `sqlite3_bind_null(stmt,index)` 的行为相符。未保存某个寄存器不等于没有那个参数。正式证据仍把这些名称标为**语义候选**，不提供可直接写进生产表的地址。

研究工具的边界据此修正：

- 原 `wxhelper-column-family` 文件名保留，但工具现在只按任意守卫聚合候选调用者；`exactArityVerified=false`、`columnMembershipVerified=false`。移除了把写入 R8/R9 错当保存传入参数的模式。
- 字节扫描的零命中只能表示该扫描器没有找到覆盖形式，不能证明死代码/没有执行路径。调用统计和序言形状也不证明 ABI 或可达性；CLI 明示身份/完整调用图未验证。
- 连续操作码名字，即便以 Init/Abortable 包围，也不等于真实数值表；工具仅给名字序号线索，真实 numbers 为空、`opcodeTablePinned=false`。对应草稿的测试规则随这项证据约束更正。
- 异常目录范围不能直接当作完整函数。候选执行入口 `0x3a5eda0` 的第一段只到 `0x3a5ee41`，下一段仅 3 条保存寄存器指令；只分析第一段会丢掉主体。后续需要解析展开链并结合控制流，而非假设“一个范围就是一个函数”。Windows 明确支持 chained unwind 信息，非叶子展开记录与叶子函数也不能用同一判据处理。[Microsoft x64 展开说明](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64?view=msvc-170)

## MediaMSG 和对象调用链候选

以下 RIP 引用先由受限扫描器提出，再从异常范围起点用 Capstone 连续解码核对；代码字节逐条与固定镜像比对。11 个解码窗口均无 resync，但仍只代表线性磁盘解码，不代表可达性/真实运行通过。

| 锚点/对象路径 | 已观察证据 | 尚不能宣称 |
| --- | --- | --- |
| `MediaMSG_Multi.db`，UTF-16 RVA `0x4f710d8` | 引用点 `0x25c9994`，所在范围起点 `0x25c9890` | 文件名与运行句柄已绑定 |
| `MediaMSG`，UTF-16 RVA `0x4f71088` | 引用点 `0x25cb477`，所在范围起点 `0x25cb1f0` | 管理器/工厂的生命周期已证明 |
| `BufInfoStorage::init`，ASCII RVA `0x4f5c510` | 引用点 `0x2516acd`，范围起点 `0x2516a00`；方法保存 this 到 R14，并读取 `[this+0x50]` | 所有注册/关闭路径稳定使用同一对象布局 |
| init → 包装方法 | `0x2516beb` 调用 `0x25bf600`，RDX 来自 `[this+0x50]`；包装方法再从虚表 `+0x10` 取对象值 | 虚表 getter 返回值就是可信 SQLite db，或与原 MultiDBMgr 根相连 |
| 包装方法 → SQL 执行候选 | `0x25bf640` 调用 `0x3a5eda0`；RCX=getter 返回值，RDX=SQL 候选，R8/R9 和第 5 栈参数为空；失败路径另一次同目标调用在 `0x25bf6bc` | 完整 sqlite3_exec 身份/ABI 全部成立 |
| init 的错误路径 | `0x2516c12` 以 `[this+0x50]` 为 RCX 调用 `0x3a9c8d0`，返回值进入错误信息路径 | 单参 errmsg 候选足以证明连接来源 |
| bind/clear | 日志引用和范围分别收敛到 `0x2514cb0`、`0x2516610`；bind 经 `0x25bc0f0` 后仍有虚调用 | clear 就等于关闭数据库，或 helper 锁能保护原生对象 |

SQL 执行候选的参数排列与公开 `sqlite3_exec` 声明一致；这只是 ABI 候选的交叉支持，源码同形不能代替完整函数/调用点确认。[上游 legacy.c](https://raw.githubusercontent.com/sqlcipher/sqlcipher/v4.2.0/src/legacy.c)

证据见 [解码窗口](P4-5d-decoded-chain-2026-10-04.json)、[包装方法和对象候选](P4-5d-runtime-owner-candidates-2026-10-04.json)、[来源与锚点](P4-5d-source-review-2026-10-04.json)。原全局根 `kMultiDBMgr=0x593abf8` → DB 对象 `+0x20` → BufInfoStorage 的链仍没有接通；本轮没有把新的命名管理区域或某个可读位置当成替代根。

## 工具复核与验收

接续并收敛既有十个研究工具及九个夹具；新 `wxhelper-db-entry-chain` 只运行固定指纹的磁盘反汇编器，从已校验范围收集调用/RIP 引用：指令必须连续、字节必须完全一致，截断/重复/伪造/范围内部起点/超限全部拒绝，区分直接函数地址与间接指针槽。E8 出现在另一个已解码指令的立即数中不会变成调用。输出始终 NO_GO，不读取地址里的运行值。

共享 PE 校验补齐 optional header 最小长度、节原始字节范围/重叠/头部别名，展开范围补齐可执行映射、展开地址与最小版本校验；RIP 寄存器编号包含 REX.R，越界目标不允许静默回绕。所有十个 CLI 的文件错误固定脱敏，两个通用工具的 CLI 也绑定完整客户端哈希。合成夹具修正了越过文件末尾的节声明，并写入合法展开信息；未借坏夹具降低校验。
